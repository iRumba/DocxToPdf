# Рабочий процесс команды

Команда работает распределённо. Весь процесс строится через GitVerse.

## Жизненный цикл задачи

### 1. Планирование

- Задача заводится в Issues (GitVerse).
- Указывается тип: feature, bug, task, improvement.
- Назначается исполнитель и label.

### 2. Разработка

- Создаётся ветка от `develop` по стратегии Git Flow.
- Ветка должна иметь префикс: `feature/`, `bugfix/`, `hotfix/`, `release/`.
- Коммиты пишутся на русском или английском, с указанием сути изменений.
- В процессе разработки допускаются промежуточные коммиты.

### 3. Pull Request

- После завершения разработки создаётся Pull Request в `develop`.
- В описании PR обязательно указать:
  - Ссылку на Issue
  - Краткое описание изменений
  - Что проверять ревьюеру

### 4. Code Review

- Исполнитель **передаёт ссылку на PR** ревьюеру.
- Ревьюер изучает изменения **на платформе** через ссылку на PR.
- Ревьюер проверяет код по критериям:
  - Соответствие философии кода (см. code-philosophy skill)
  - Отсутствие ошибок и уязвимостей
  - Тесты
  - Документация
- Комментарии оставляются **на платформе** (в интерфейсе PR).
- По итогу ревьюер сообщает оркестратору:
  - ✅ «Замечаний нет, можно merge»
  - ❌ «Есть замечания: ...» (список с номерами)
- Если PR не проходит — исполнитель исправляет замечания в той же ветке, PR обновляется автоматически.
- Цикл повторяется, пока ревьюер не утвердит (✅).

### 5. Слияние

- После approve → слияние в `develop`.
- Ветка удаляется.
- Ветка `main` — только через `release/*` или `hotfix/*`.

### 6. Релиз

- Создаётся ветка `release/X.Y.Z`.
- Финальное тестирование.
- PR в `main` с тегом версии.
- После слияния → тег и релиз.
